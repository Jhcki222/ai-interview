# 이종혁 경험 카드

이 문서는 자기소개서 작성 시 사용할 수 있는 경험 카드다. 2026-10-18 성과지표 정합성 검수본을 바탕으로 2026-10-22 수상, 교육, 동아리, 공동연구 관련 최신 확인 사항을 반영했다.

> **수치 및 출처 관리 원칙**
>
> - 한 프로젝트의 성과를 다른 프로젝트에 복사하지 않는다. **노후하우 Recall@10은 0.68 → 0.85, COLLABO Recall@5는 0.59 → 0.88**로 구분한다. K가 다르므로 직접 비교하지 않는다.
> - `확인된 기록`은 사용자 제공 수치나 이전 지원 자료에 기록된 값을 뜻하며, 동일 데이터셋의 원본 평가 로그를 모두 확보했다는 뜻은 아니다. 지표 단위, 평가 기준 및 변경 실험 시점이 필요한 경우 별도 기록한다.
> - 새로 제시된 Kaggle VQA 평가지표는 플랫폼 Score(0.70837 → 0.96812)로 표기한다. 채점 방식이 확인되지 않은 상태에서 Accuracy, F1, 정답률로 바꾸지 않는다.
> - 시나리오 49/53은 **92.5%**(소수 첫째 자리 반올림). 퍼센트와 퍼센트포인트는 구별한다.

## 기본 프로필

- 이름: 이종혁
- 전공: 동국대학교 컴퓨터공학과 학사
- 지향 직무: 백엔드 개발자
- 관심 분야: Backend Engineering, AI Service, Cloud, System Architecture
- 핵심 강점: AI 기능을 실제 사용자 서비스에 빠르게 적용하고, 백엔드·데이터·운영까지 연결해 구현하는 능력
- 보완점: 임베디드·하드웨어 등 로우레벨 영역에 대한 이해가 상대적으로 부족해 지속적으로 보완 중
- 자격: SQLD, 정보처리기사
- 주요 기술:
  - Backend: Java, Spring Boot, MySQL, MongoDB, PostgreSQL, FastAPI
  - AI: LangChain, Vector DB, LLM
  - Frontend: React.js, Next.js, TypeScript, JavaScript, HTML/CSS
  - DevOps: Docker, AWS, Jenkins, ELK, SonarQube, Vercel

  - 금융위원회, 한국벤처투자, 금융감독원 등 외부 OpenAPI를 활용해 예/적금, 펀드, 연금저축 금융 상품 데이터를 수집
  - 요구사항 분석, 화면 설계, 페르소나/타겟 설정, 기능 명세서 작성
  - UX/UI 설계, ERD, 시스템 아키텍처, API 명세서, 데이터 수집 파이프라인, AI 서버 아키텍처 설계
- 주요 행동:
  - 요구사항 분석, 화면 설계, 페르소나/타겟 설정, 기능 명세, UX/UI, ERD, 시스템 아키텍처, API 명세, 데이터 수집 파이프라인과 AI 서버 아키텍처 설계
  - 클라이언트, 메인 백엔드 서버, AI 서버 전체 코드 리뷰 및 검수
  - 메인·인증·리소스 서버에 SOLID, 계층형 아키텍처, 예외 처리, 보안, 테스트 기준을 담은 공통 코드 컨벤션을 적용해 코드 작성과 리뷰 기준 통일
  - KCC 제출본 기준 4개 서버 저장소에 공통 예외 처리·트랜잭션 규칙과 장애 대응 원칙을 작성
  - Jenkins CI 파이프라인에 SonarQube를 연동해 정적 코드 분석을 자동화하고, JaCoCo 단위·통합 테스트 커버리지를 85% 이상 유지
  - 세 백엔드 저장소에 Gemini Code Assist 설정을 적용해 PR 단위 AI 코드 리뷰 자동화
  - AI를 단순 코드 생성 도구가 아니라 팀의 공통 기준을 반복 점검하는 협업 도구로 활용하고, 자동 리뷰 결과는 변경 의도·기존 구조·실행 결과를 팀원이 다시 확인한 뒤 필요한 내용만 반영
  - AI 서버 지연으로 초기 화면 진입이 늦어지는 문제를 해결하기 위해 추천 상품 컴포넌트를 Dynamic Import로 Lazy Loading
  - AI 서버의 표준 SSE 응답을 디코딩해 청크와 JSON 객체로 파싱하는 커스텀 스트리밍 챗봇을 구현하고 초기 응답 대기시간 개선(기존 제출 자료에 약 70% 개선으로 기록, 비교 조건 확인 필요)
  - 스트리밍 응답을 일반 텍스트, 상품 추천, 추천 질문, 다른 기능 이동의 4가지 유형으로 분기해 UI 업데이트
  - Cursor-based 페이지네이션과 인피니트 스크롤로 최근 채팅을 5개씩 조회하여 초기 렌더링과 DB 조회 부하 완화
  - Zustand로 자산 추가 입력 상태를 관리하고, 마이데이터 연동 및 포트폴리오 생성 여부에 따른 메인 화면 접근 제어 구현
  - PWA를 적용해 앱 설치와 불안정한 네트워크 환경에서의 사용성을 고려
  - 영상편지 업로드 시 S3 Presigned URL과 Multipart Upload를 사용하고, 한 번에 3개 청크를 병렬 전송하며 진행률을 실시간 표시
  - 실제 마이데이터 표준 API 명세와 가이드라인을 분석하고, 메인, 인증(Authorization), 리소스(Resource) 서버로 책임을 분리한 모의 마이데이터 환경 구현
  - Spring Authorization Server 기반 OAuth2 Authorization Code 흐름과 금융인증 화면, 인증 후 원래 인가 요청으로 복귀하는 세션 SecurityContext, 사용자 동의 화면을 구성
  - 인증 서버에서 2,048비트 RSA 키와 JWK를 이용해 JWT Access Token을 발급하고, 암호화된 CI를 토큰의 subject로 전달하도록 인증 흐름 구성
  - 메인 서버에서 Authorization Code를 토큰 엔드포인트와 교환하고, Access Token은 사용자별 Redis 키에 `expires_in` 기반 TTL로 저장하며 Refresh Token과 scope는 RDB에 분리 보관
  - 리소스 서버 호출이 401을 반환하면 Refresh Token으로 Access Token을 갱신한 뒤 한 번 재호출하고, 재발급 실패와 서버 오류를 도메인 예외로 구분
  - 리소스 서버를 Stateless OAuth2 Resource Server로 구성하고, JWT subject의 암호화된 CI를 복호화한 뒤 HMAC-SHA256으로 해싱해 내부 금융 사용자 ID로 치환하는 커스텀 인증 Converter 구현
  - 인증된 사용자 ID를 Repository 조회 조건에 포함해 타인 금융 데이터 접근을 차단하고, 자산 및 연금(DC/IRP) 관계는 Fetch Join으로 조회한 뒤 응답 DTO로 평탄화
  - 리소스 서버에서 받은 자산, 부채, 연금 데이터를 메인 서버 트랜잭션 안에서 정규화·재동기화하고, 자산 합계에서 부채를 차감한 순자산과 마이데이터 연동 상태를 함께 갱신
  - 이름, 전화번호, CI 등 원본 복원이 필요한 개인정보는 랜덤 IV를 사용하는 AES/GCM으로 암호화하고, 동등 검색이 필요한 컬럼에는 HMAC-SHA256 값을 별도로 저장해 기밀성과 조회 가능성을 함께 확보
  - JPA `AttributeConverter`로 개인정보 암·복호화를 저장·조회 과정에 적용하고, 이름과 전화번호 검색용 Hash 컬럼에는 인덱스를 구성했으며 CI(UserCode)는 별도 Hash 컬럼으로 분리
  - SMS 인증번호와 확인 상태를 Caffeine Cache에 3분 TTL로 보관해 인증 정보의 유효시간 제한
  - 민감 데이터와 Jenkins·마이데이터 서버는 온프레미스에 두고, 실제 서비스가 구동되는 AWS 클라우드와 터널링으로 연결한 하이브리드 아키텍처 구축
  - Route 53와 WAF를 거친 요청을 NAT Instance를 통해 Private Subnet의 서비스 서버로 전달하고, Bastion Host와 SSH ProxyJump 및 접속 키 분리로 관리 경로 제한
  - Jenkins 접근을 허용된 관리자 IP로 제한하고 Credential 기능으로 키 파일과 환경 변수를 암호화해 관리
  - 인증 서버와 리소스 서버에 `AbstractRoutingDataSource`와 `LazyConnectionDataSourceProxy`를 적용해 `readOnly` 트랜잭션은 Slave, 쓰기 트랜잭션은 Master로 지연 라우팅
  - Master DB는 정합성이 중요한 쓰기 작업, Slave DB는 빈번한 조회 작업을 담당하도록 분리하고 HAProxy로 DB 트래픽을 로드밸런싱
  - 금융 상품의 신선도를 유지하기 위한 데이터 수집 및 적재 자동화 파이프라인 설계
  - 온프레미스 Airflow에 추출, 전처리, 임베딩, 적재 Task로 구성된 ETL DAG를 구축하고 매일 새벽 3시에 순차 실행
  - 수집 후 만료 상품을 삭제하고 임베딩 누락 상품을 재처리하여 데이터 신선도와 정합성 유지
  - 연금저축 297개, 펀드 971개, 예·적금 58개 등 총 1,326개 금융 상품을 `gemini-embedding-001`로 768차원 벡터화해 MongoDB Atlas에 적재
  - 복잡한 금융 데이터에 적합한 유연한 스키마와 내장 Vector Search를 근거로 MongoDB Atlas를 선택하고, 별도 벡터 DB 없이 Hybrid Search 기반 RAG 구현
  - 기존 벡터 검색의 낮은 추천 적중률을 개선하기 위해 Hybrid Search와 재랭킹을 적용하여 Recall@10을 0.68에서 0.85로, NDCG@10을 0.64에서 0.79로 개선
  - 후보 검색 범위와 재랭킹 대상을 조정하며 검색 응답시간을 최적화했다. **약 42%와 약 50% 단축 기록이 상충**하여 실험 조건과 측정 원본 확인 전에는 단일 수치를 확정하지 않는다.
  - SQLAlchemy로 MySQL 사용자 정보를 조회·텍스트화한 뒤 상품과 동일한 차원으로 임베딩하고, Cosine 유사도 기반 Vector Search와 RAG Chain으로 후보 상품 추출
  - StateGraph로 후보 상품을 검증·전처리한 뒤 클라이언트에 서빙
  - LLM의 요청 해석과 상품 적합성 판단을 분리하고, LangGraph의 검색·검증·응답 단계에서 최신 고객 자산·투자 성향·상품 구조·가입조건·비선호 이력을 검증한 뒤 적합한 상품만 응답하도록 고도화(상세 §1-C)
  - 위험등급이 없는 상품은 공식 자료의 확인 가능한 특성을 근거로 내부 위험도를 분류하고, 공식 등급과 구분하여 표시하며 추천 근거·제외 사유를 MongoDB에 기록
  - 사용자 ID/세션 ID별 대화 기록을 MongoDB에 저장하고 Cursor-based 페이지네이션과 인피니트 스크롤을 적용해 최근 내역을 5개씩 조회
  - 스트리밍 답변의 키워드 태그를 정규표현식으로 추출해 후속 질문 UI로 재구성하고, 추천 시 상품 카드와 가입 링크 제공
  - 좋아요/싫어요 이력을 상품 ID 기준으로 분류해 비선호 상품을 제외하고 선호 상품을 상단에 배치하는 실시간 리랭킹 구현
  - 시스템 프롬프트와 서비스 블랙리스트로 Prompt Injection을 차단하고, 금융·비금융 질문 분류 및 입력값 검증 로직 구현
  - 투자 상품에는 원금 손실 가능성을 명시하고 단정적 수익 표현을 제한했으며, 사용자 성향에 맞지 않는 고위험 상품을 추천 순위에서 제외
  - LLM API 사용자별 호출량 모니터링 API 및 관리자 대시보드 구현. 후속 고도화에서 JWT 인증 기반 공통 게이트웨이, Redis Lua 전체·사용자별 호출 제한과 모델별 동시 실행 제어, 429 재시도, 실제 토큰 계측 및 관리자 집계로 확장(상세 §1-D)
  - 관리자 통계 API의 지연 가능성을 단일 쿼리의 속도 문제가 아니라 애플리케이션 반복문 내부에서 DB I/O를 수행하는 데이터 접근 구조의 문제로 분석하고, 목록 조회 뒤 각 결과의 추가 데이터를 반복 조회한다는 점에서 전통적인 ORM Lazy Loading과 발생 맥락은 다르지만 N+1과 유사한 패턴으로 판단
  - 현재 페이지의 `user_id`를 먼저 수집한 뒤 MongoDB Aggregation Pipeline의 `$match`·`$in`으로 대상 사용자의 로그만 일괄 조회하고, `$group`과 조건부 합계로 사용자별 user/assistant 메시지 수를 한 번에 집계
  - 좋아요와 싫어요 통계도 별도의 Aggregation Pipeline에서 `$match`·`$in`과 `$group`을 사용해 사용자별로 일괄 계산하고, 만족도는 집계된 likes와 dislikes를 바탕으로 애플리케이션에서 계산
  - MongoDB Aggregation 결과를 `user_id`가 key인 Dictionary로 변환해 사용자 목록 반복문에서는 추가 DB 조회 없이 메모리의 통계 값을 매핑하도록 변경
  - 채팅 로그 API에서는 Aggregation 결과의 `user_id`를 모아 MySQL `WHERE IN` Batch Query로 사용자 이름을 일괄 조회하고, `user_id → name` Map을 만든 뒤 반복문에서 조회하도록 변경
  - 저장소를 가로지르는 조인이 어려운 MySQL·MongoDB 혼합 구조에서 MongoDB에는 필터링·그룹 집계를, MySQL에는 관계형 조건 기반 일괄 조회를 맡기고 애플리케이션은 결과 매핑을 담당하도록 책임 분리
  - 사용자 채팅 내용 적재 및 민감 키워드 모니터링
  - JWT 인증/인가, OAuth2.0 소셜 로그인, Redis 기반 토큰 관리, 로그아웃 토큰 블랙리스트, Refresh Token 재발급, SMS 인증, BCrypt 암호화 구현
  - 마이데이터 기반 포트폴리오 조회/진단 API와 예/적금 시뮬레이션 API 구현
  - GlobalExceptionHandler, CustomException, JUnit/Pytest 테스트 적용
  - ELK Stack 기반 중앙 집중형 로그 모니터링 환경 구축
- 성과:
  - SSE 기반 커스텀 스트리밍으로 챗봇 초기 응답속도 70% 개선(초기 응답의 측정 시작점 및 비교 조건은 확인 필요)

- 주의:

  - 코드상 OAuth2 `state`는 고정값이며 검증 로직이 구현되지 않았으므로 CSRF 방어를 완성했다고 표현하지 않는다. PKCE, scope 기반 API 인가, 영속 서명키 운영도 구현 사실로 추가하지 않는다.

### 1-A. 노후하우 AI 서버 고도화: 배치·CDC·추천 최신성·장애 복구

- 정리 기준일: 2026-10-07. **KnowWhoHow 동일 프로젝트의 개발 및 고도화 과정**에서 진행한 작업이다. 최초 2025년 발표 시점의 구현과 2026년 10월 후속 AI 서버 개발 및 검증 시점은 구분한다. 별개 서비스로 취급하지 않는다.
- 대상 저장소: `C:/ai-server`. 이 AI 서버는 별도 프로젝트가 아니라 **KnowWhoHow / 노후하우**의 추천·상담·데이터 파이프라인 서버다.
- 이번 목표: 사용자의 자산·투자 성향·은퇴 상태·마이데이터 연동 상태가 바뀌면 추천 문맥에도 반영되도록 리팩토링하고, 배치와 CDC의 역할을 구분하며, 중단·재전달·외부 API 실패에 대한 복구를 구현한다.
- 기술: Python, FastAPI, SQLAlchemy, MySQL, MongoDB/PyMongo, Airflow, Debezium, Kafka, LangGraph/LangChain, Gemini 임베딩, Docker Compose, Pytest.
- 수행 범위: 기존 코드 분석 → 최신성 문제 정의 → 공통 페르소나/원천 조회/저장 계층 분리 → CDC 도입 → 장애 정책·진단·재처리 구현 → 자동 테스트와 실제 컨테이너 장애 주입 → 운영 문서 정리. AI 도구를 활용한 후속 개발 작업이며 면접에서는 본인이 이해·설명할 수 있는 설계 및 검증 범위로 기술한다.

#### 기존 AI 서버와 배치 구현

- FastAPI로 사용자 벡터화, 개인화 상품 추천, SSE 상담, 대화 이력·피드백·관리자 API를 제공한다.
- MySQL의 사용자·자산·은퇴 목표·관심 키워드를 페르소나로 구성하고 MongoDB에 저장한다. 온라인 추천은 페르소나 **텍스트**를 에이전트 문맥으로 사용하며, 저장된 사용자 임베딩만으로 추천이 결정되는 구조라고 설명하지 않는다.
- LangGraph 에이전트가 예금·적금·연금저축·펀드별 검색 도구를 선택하고 MongoDB Atlas Vector Search로 후보를 검색한다. 예금/적금은 메타데이터로 구분하고 상품·혜택·추천 이유를 구조화한 응답을 생성한다.
- 상품 좋아요·싫어요 로그로 비선호 상품을 제외하고 선호 상품을 상단에 배치하며, 사용자/세션별 상담 문맥과 대화 기록을 관리한다.
- Airflow 상품 수집 DAG는 금융감독원·금융위원회·한국벤처투자 등의 외부 API를 수집하고 전처리·검색용 `rag_text` 생성·임베딩·MongoDB 적재를 수행한다. 상품군별 수집과 컬렉션 통합·만료 상품 정리·누락 임베딩 backfill을 별도 DAG로 구성한다.
- 확인 가능한 DAG: `pipeline_fss_deposit.py`, `pipeline_fss_saving.py`, `pipeline_fss_annuity.py`, `pipeline_fsc_fund.py`, `pipeline_kvic_fund.py`, `pipeline_merge_collections.py`, `pipeline_cleanup_expired.py`, `pipeline_embedding_backfill.py`.
- 배치는 상품 목록의 정기 수집·유지보수에, CDC는 개인별 금융 상태 변경에 적용한다. 변경 빈도와 추천에 미치는 영향이 다른 두 데이터를 같은 주기성 작업으로 처리하지 않도록 구분했다.
- 이번 작업에서는 기존 상품 Airflow DAG를 유지했다. 원본 수집 데이터를 S3/MinIO에 별도 보존하는 레이크, XCom을 객체 저장소 참조로 전환하는 작업, 별도 정규화 저장 계층은 제안 가능한 후속 개선이며 구현 성과로 추가하지 않는다. 모든 DAG의 실행 시각이 동일하다고 단정하지 않는다.

#### 문제 정의와 CDC 도입의 명분

- 기존에는 MongoDB의 페르소나를 재사용하므로 MySQL의 잔액·투자 성향·은퇴 상태가 바뀌어도 벡터화 API를 다시 호출하지 않으면 이전 금융 정보가 추천 문맥으로 남을 수 있었다.
- 추천 품질은 상품 검색 정확도뿐 아니라 사용자의 **현재 상황**에도 의존한다. 예를 들어 자산이 감소하거나 은퇴 상태가 바뀌었는데 과거 자산·소득 전제를 유지하면 현재 상태에 맞는 개인화 추천이라고 보기 어렵다.
- 금융 상품 배치 주기만 단축해도 사용자 상태 변경 문제는 해결되지 않는다. 사용자 원천 변경을 별도로 감지하고 추천용 상태를 갱신해야 했다.
- CDC 이벤트는 상태 변화 감지와 갱신 대상 식별에 사용한다. 이벤트 금액을 누적 계산하지 않고 원천 DB의 최신 committed 상태를 다시 읽어 추천용 projection을 구성한다.
- Kafka는 현재 트래픽 규모에서 필수라는 결론으로 도입한 것이 아니다. 변경 이벤트 보존, 소비자 offset 기반 재소비, 원천 변경 감지와 갱신 처리 분리, 장애 후 복구 절차를 구현하려는 목적에서 선택했다. 대용량 처리 필요성이나 여러 소비자의 실운영 실적은 측정·입증하지 않았다.
- 사용자 요청이 없어도 projection을 지속적으로 갱신하고, 중단 중 발생한 변경을 복구할 수 있도록 했다. 원천 변경을 이벤트로 감지하는 경로와 추천 시 최신성을 보완하는 경로를 함께 마련했다.

#### 리팩토링과 구체적 구현

1. **공통 페르소나 생성**: `persona.py`에 결정적인 순수 함수를 두어 입력이 같으면 같은 텍스트를 생성하도록 정리했다. 실제 생년월일에 따른 연령, 투자 성향, 소득·목표, 은퇴·마이데이터 상태, 자산 구성을 반영하고 `0`과 `False`도 유효한 값으로 처리한다. 키워드·자산을 정렬해 입력 순서만 바뀌어도 불필요한 임베딩이 발생하는 문제를 줄였다.
2. **금액 정확성**: `Decimal`로 금액을 처리하고 억/만원 단위 반올림을 제거했다. 자산 상세의 총자산·대출·순자산을 구분하고 원천 `asset_total`도 별도로 표현해 작은 잔액 변화가 텍스트에서 사라지지 않게 했다.
3. **일관된 원천 조회**: `user_source.py`에서 재사용 가능한 SQLAlchemy 엔진을 사용하고 사용자·추가 정보·자산·키워드를 하나의 MySQL REPEATABLE READ 트랜잭션으로 읽는다. 사용자 조회 컬럼에서 비밀번호·전화번호를 제외하고 사용자 미존재를 별도 예외로 처리한다.
4. **단일 저장 경로**: `user_projection.py`로 MongoDB 페르소나 게시·삭제·임베딩 상태 관리를 통합했다. 기존 profile/vector 서비스와 벡터화 서비스가 같은 공통 경로를 사용하도록 바꿔 고정된 연령이나 중복 생성 경로의 불일치를 줄였다.
5. **텍스트와 임베딩 분리**: 최신 페르소나를 먼저 게시한 뒤 별도 embedding worker가 벡터를 갱신한다. 외부 임베딩 실패가 최신 금융 텍스트 반영을 막지 않는다. 페르소나 SHA-256과 임베딩 대상 모델을 확인해 내용·모델이 같으면 재임베딩을 건너뛰고, 내용이 바뀌면 이전 벡터를 제거한다.
6. **동시 갱신 방어**: 원천 읽기 전에 갱신 revision을 예약하고 조건부 저장해 늦게 끝난 이전 조회가 더 최근 조회를 덮어쓰지 않게 했다. 임베딩 결과 저장 시 텍스트 hash·모델·삭제 여부·임대 토큰을 검사해 오래된 벡터 게시와 삭제 사용자 복원을 막는다.
7. **추천·상담 최신성 보완**: 추천과 챗봇 요청에서 MySQL을 다시 읽고 최신 페르소나를 사용한다. 한 상담 요청에서 상품 추천으로 넘어갈 때 같은 페르소나 스냅샷을 전달해 요청 안에서 서로 다른 사용자 상태가 섞이지 않도록 했다. 동기 DB I/O는 `asyncio.to_thread`로 분리하고 임베딩 클라이언트는 필요할 때 생성한다.
8. **CDC 변경 감지**: MySQL 초기 snapshot/binlog → Debezium → Kafka → CDC 소비자 → MongoDB 영속 갱신 큐 → persona worker → user projection → embedding worker로 연결했다. 감지 테이블은 `users`, `user_info`, `assets`, `user_keyword`, `keyword`다.
9. **민감 데이터 최소화**: Debezium 컬럼 필터에는 사용자·자산·키워드의 식별/연결용 컬럼만 포함한다. Kafka에는 비밀번호·연락처·자산 금액 원문을 복제하지 않고, 실제 금융 문맥은 권한 있는 원천 조회로 구성한다.
10. **변경·삭제 라우팅**: 자산 소유자 변경은 before/after의 두 사용자 모두 갱신한다. 삭제는 before 정보를 활용한다. 키워드 FK cascade 삭제로 현재 SQL 관계가 사라졌을 때는 projection에 보존한 `keyword_ids`도 조회해 영향 사용자를 찾는다. 사용자 삭제는 텍스트·벡터를 제거한 tombstone으로 반영한다.
11. **재전달 처리**: MongoDB에 journal/majority 쓰기로 갱신 작업을 영속 등록한 후에만 Kafka offset을 수동 커밋한다. 저장 성공 후 커밋 전에 종료되어 같은 이벤트를 다시 받더라도 현재 원천을 다시 읽는다. 사용자별 `generation`으로 처리 중 들어온 새 이벤트가 이전 작업 완료 처리에 지워지지 않도록 했다.
12. **전체 재조정**: 원천의 사용자와 기존 비삭제 projection의 사용자 ID를 갱신 큐에 넣는 reconcile을 제공한다. 원천에서 사라진 사용자의 삭제 누락도 재확인하며 기본 15분 간격의 reconciliation worker로 반복한다.
13. **실행 구성**: 독립적인 CDC용 Docker Compose와 데모 MySQL fixture를 제공했다. MySQL 8.4, Kafka 4.1.2, Debezium 3.3.1.Final, MongoDB 7.0 및 소비자·페르소나·임베딩·재조정 워커를 연결하고 Connector 설정을 idempotent PUT으로 등록한다. 실제 `user_keyword` 복합키 `(user_id, keyword_id)`를 반영했다.

| 변경 API에서 직접 갱신                 | 통제된 쓰기 경로에서는 간단하고 즉시 후속 처리를 호출할 수 있음                     | 모든 변경 경로의 연동 필요, 원천 저장과 후속 처리 실패 사이 정합성 문제. 외부 변경·직접 SQL도 반영하려면 별도 보완 필요                         |
| Transactional Outbox                   | 업무 변경과 발행할 이벤트를 같은 DB 트랜잭션에 저장해 이중 쓰기 문제 완화           | 원천 애플리케이션 수정·outbox 처리 필요. Kafka와 함께 사용할 수 있는 패턴이므로 Kafka와 완전한 대체 관계로 설명하지 않음                        |
| Kafka 없는 Debezium 배포 / 다른 메시징 | 요구 규모와 운영 여건에 맞춰 구성 단순화 가능                                       | 필요한 sink·버퍼·재처리 기능을 별도로 비교해야 함. RabbitMQ Streams도 재생 가능한 구조를 제공하므로 재소비가 Kafka만의 기능이라고 주장하지 않음 |
| 이벤트마다 원천 재조회                 | 중복·역순 이벤트에서 금액을 잘못 누적하지 않고 현재 추천 상태로 수렴                | 중간 상태·전체 변경 이력은 보존하지 않음. 이벤트 당시 상태 재현·감사 원장 목적에는 별도 설계 필요                                               |
| 페르소나 게시와 임베딩 분리            | 외부 임베딩 실패 중에도 최신 텍스트 사용, 불변 텍스트 재임베딩 생략                 | 최신 텍스트와 벡터의 완료 시점이 다름. pending/failed 관리와 늦은 결과 방어 필요                                                                |
| hash·revision·generation·lease         | 재전달·동시 조회·워커 종료 시 낡은 결과 덮어쓰기와 작업 유실 방어                   | 상태 관리가 복잡해지고 조건부 쓰기 필요. 전체 Kafka–MongoDB exactly-once를 구현한 것은 아님                                                     |
| MongoDB 영속 갱신 큐                   | projection과 작업 상태를 같은 저장소에서 관리하며 원자적 claim 가능                 | 저장소 장애에 함께 영향받음. 단일 노드의 majority 설정은 복제본 failover나 호스트 장애 HA를 의미하지 않음                                       |

- 면접에서 Kafka 선택을 설명할 핵심: 현재 규모에서 필수였다고 과장하지 않고, 최신성 문제 자체는 원천 조회로도 풀 수 있음을 인정한다. Kafka는 요청 외 자동 갱신과 보존된 변경의 재소비·복구를 구현하려는 선택이며, 이 이점과 운영 복잡성을 함께 평가했다고 설명한다.
- CDC는 비동기이므로 DB commit 직후 무지연 반영을 보장하지 않는다. 신규 요청이 원천을 읽은 시점의 스냅샷을 사용하며, 읽기 이후 또는 SSE 응답 생성 중의 자산 변경까지 자동 반영·재추천하지 않는다.

| MongoDB 큐/격리 저장 실패   | 영속 기록 전 offset 커밋 금지                                                                   | MongoDB 복구 후 동일 이벤트 재소비                                                    |
| 작업 claim 후 강제 종료     | 원자적 claim, 기본 120초 lease와 토큰                                                           | lease 만료 후 다른 워커가 처리. 이전 토큰으로 새 작업 ack/fail 불가                   |
| 처리 중 새 이벤트 도착      | 사용자별 generation 증가                                                                        | 이전 generation의 완료가 새 갱신 요청을 삭제하지 않음                                 |
| MySQL 원천 조회 실패        | bounded retry 후 failed 보관. 추천은 오래된 금융정보로 fallback하지 않음                        | 원인 해결 후 재처리·전체 재조정                                                       |
| 임베딩 API 실패             | 최신 텍스트 유지, jitter 지수 backoff, 기본 최대 5회 후 failed, 연속 3회 실패 시 30초 호출 중단 | API 복구 후 임베딩만 재처리                                                           |
| 형식이 잘못된 CDC 메시지    | topic/partition/offset·SHA-256·바이트 수·오류 유형만 MongoDB에 영속 격리 후 커밋                | 후속 정상 이벤트 계속 처리. 원문 재소비·검토한 사용자 지정·전체 재조정 중 선택        |
| DB·네트워크 장애            | 입력 형식 오류와 구분하고 poison 메시지로 격리하지 않음                                         | offset을 넘기지 않고 기반 시스템 복구 후 재소비                                       |

| Connector/task FAILED       | REST 상태 진단에 비정상 표시                                                                    | 원인 수정 후 실패한 connector/task만 재시작                                           |
| 원천 binlog 유실            | 단순 재시작으로 해결된다고 가정하지 않음                                                        | snapshot·schema history·offset 재구축 계획 필요. 파괴적인 초기화는 자동 실행하지 않음 |
| SIGTERM/SIGINT·강제 종료    | 정상 종료 신호 처리, 소비자 close, Compose 종료 유예 45초                                       | 유예 초과 강제 종료는 offset·영속 큐·lease로 재처리                                   |

- 재시도는 기본 2초에서 지수 증가하고 상한 60초에 0.8~1.0 jitter를 적용한다. 기본 최대 시도 5회, lease 120초는 설정으로 조정한다.
- MongoDB server selection/connect timeout 5초, socket timeout 10초, MySQL connect 5초·read/write 10초, 임베딩 요청 timeout 30초를 설정했다. 임베딩 SDK 내부 재시도로 전체 처리 시간이 lease를 넘을 수 있으며, 이 경우 외부 호출 중복 가능성은 남고 조건부 저장으로 낡은 결과 게시를 방어한다.
- worker heartbeat는 로컬 파일을 원자적으로 갱신하고 MongoDB에도 기록한다. 진단에는 워커 생존, MySQL 연결, Connector/task 상태, Kafka lag·offset gap, 큐 상태·최고 대기시간·실패 수를 포함한다. Kafka lag 진단은 소비자 그룹에 가입하거나 offset을 커밋하지 않는다.
- `/health`는 API 생존, `/health/ready`는 MySQL·MongoDB 접근 가능성을 확인한다. 원천/저장소 장애는 503, CDC·임베딩만 비정상이고 원천 조회가 가능하면 API는 200을 유지한다. `CDC_MONITORING_ENABLED`로 파이프라인 진단을 readiness에 포함한다.
- CLI: `python -m app.pipelines.worker`의 `status`, `failures`, `retry-refresh --id <user_id>`, `retry-embedding --id <user_id>`, `retry-cdc --id <topic:partition:offset>`, `reconcile`, `restart-connector`를 제공한다.
- `retry-cdc`는 원 Kafka 위치에서 다시 읽으며 main consumer offset을 변경하지 않는다. 원문이 영구적으로 잘못되었거나 보존 범위를 벗어났다면 검토한 `--user-id` 또는 `--reconcile`로 현재 상태 갱신을 등록한다. 등록 실패 시 격리 상태를 유지한다.
- 재등록의 `resubmitted`, Connector 재시작 HTTP 202는 요청 수락을 뜻한다. 실제 작업 완료·Connector RUNNING·실패/대기 건수를 별도로 확인한다.
- Docker `unhealthy`만으로 컨테이너가 자동 재시작되는 것은 아니다. 프로세스 종료는 restart 정책으로 처리하며 살아 있지만 멈춘 프로세스는 운영자 또는 별도 감독 기능이 필요하다. 외부 알림·자동 페이징·다중 노드 HA는 이번 구현 범위에 포함하지 않는다.

| 스키마 불일치 수정    | 데모 `user_keyword`에 실제 스키마와 다른 단일 ID를 가정하면 Connector 설정과 변경 라우팅이 어긋남                                   | 실제 복합키 `(user_id, keyword_id)` 기준으로 fixture·컬럼 설정 정정                                                            |
| 기존 구현 개선        | 중복 페르소나 경로의 고정 연령, 금액 반올림, 0/False 누락이 현재 사용자 상태를 왜곡할 수 있음                                       | 공통 순수 builder, 생년월일 기반 연령, Decimal, 명시적인 빈 값 판정으로 통합                                                   |
| 삭제 경계조건 방어    | FK cascade 이후 현재 사용자–키워드 관계만 보면 삭제 영향 사용자를 놓칠 수 있음                                                      | projection의 `keyword_ids` 역조회와 현재 SQL 관계를 함께 사용                                                                  |
| 동시성 위험 방어      | 느린 원천 조회·임베딩이 더 최신 결과를 덮어쓰거나 삭제 사용자를 다시 만들 수 있음                                                   | read 전 revision 예약, hash/model/deleted/lease 토큰 CAS, tombstone 및 경계조건 테스트                                         |
| 메시지 처리 위험 방어 | poison 메시지에서 계속 실패하면 후속 정상 변경이 처리되지 않음                                                                      | 입력 오류만 영속 격리 후 커밋. 저장소 장애는 커밋하지 않는 정책을 구분하고 실제 Kafka 메시지로 검증                            |

- 실제로 관찰한 개발/실험 오류와, 운영 장애를 예방하기 위해 설계·테스트한 경계조건을 구분한다. 위 동시성·FK cascade 방어를 실제 운영 장애 이력으로 꾸며 쓰지 않는다.

#### 개선 성과와 정량 해석

- 수동 벡터화 재호출에 의존하던 사용자 문맥 갱신을 CDC 자동 갱신과 추천 시 원천 재조회로 보완했다. 상태 변화가 추천에 반영되는 경로와 실패 후 복구 경로를 코드·문서·테스트로 만들었다.

#### 남은 개선과 구현 한계

- 운영 지표 측정: commit→페르소나/임베딩 완료 p50·p95, API 지연, consumer lag, 큐 최고 대기시간, 재시도, 임베딩 호출 수·비용, 부하 증가 시 처리량. 현재 복구 fixture 수치만으로 운영 SLA나 확장성을 제시하지 않는다.
- 원천 재조회 비용을 측정한 후 허용 가능한 금융 상태 지연을 정의하고 캐시 중심 읽기 정책을 검토한다. 아직 해당 정책을 도입하지 않았다.
- 다중 노드 Kafka/MongoDB, 호스트·네트워크 장애, 복제본 failover, 원천 binlog 유실 후 재snapshot, 외부 알림과 감독 기능, 운영 계정 권한·TLS는 별도 운영 고도화다. 과거 온프레미스 물리 서버 장애의 근본 원인을 이번 단일 노드 CDC로 해결했다고 쓰지 않는다.
- 전체 추천 E2E는 기존 MongoDB Atlas 상품 데이터와 Vector Search 인덱스가 있는 환경에서 별도로 검증해야 한다. 로컬 MongoDB fixture는 Atlas 검색 인덱스를 제공하지 않고 금융 상품을 seed하지 않는다.
- 기존 관리자 테스트 경로 및 SSE mock 경고 정리, 외부 임베딩 실제 의존성과 retry/lease 설정 검증, 정기 재조정 규모·부하 검증이 남는다.
- 이벤트는 현재 상태 갱신용이다. 모든 자산 중간 상태의 감사 이력, 분산 exactly-once, 진행 중 SSE 자동 재추천, MySQL 장애 중 stale 금융정보 응답, Kafka 보존 기간 밖 과거 이벤트 복원은 구현 성과가 아니다.

### 1-C. 노후하우 금융상품 추천 고도화: LLM 역할 분리·적합성 검증·상품 근거 보강

- 역할: 시니어 자산관리 서비스 노후하우의 기술리더로 금융상품 추천 에이전트 설계 및 고도화
- 핵심 성과: **동일한 300개 평가 데이터셋에서 부적합 상품 추천률을 18%에서 2%로 개선(16%p 감소)**
- 주요 기술: Python, FastAPI, LangGraph StateGraph, MongoDB Atlas Vector Search, MySQL, SQLAlchemy, Pydantic, Pytest

#### 문제 상황과 원인 분석

- 초기에는 LLM이 고객의 투자 성향을 문맥으로 파악하고도 고수익·고위험 상품이나 요청 조건과 무관한 상품을 추천하는 문제가 발생했다.
- 검색 도구가 반환한 후보 중 무엇이 적합한지 판단하는 책임까지 LLM에 맡겼고, 일반 요청에 특정 상품군을 반드시 포함하거나 빈 목록을 반환하지 못하도록 한 프롬프트가 부적합 후보의 추천을 유도할 수 있었다.
- 프롬프트를 수정하는 방식만으로는 성향·자금·가입조건·비선호 이력을 매번 일관되게 적용하기 어려웠다. 추천 결과를 생성한 뒤 싫어요 상품을 제거하는 방식도 답변 생성 단계의 오류를 막기에는 늦었다.
- 원천 상품 데이터에 위험등급이 없다는 제약도 있었다. 상품명이나 LLM의 추정으로 등급을 채우는 대신, 공식 자료에서 확인한 상품 특성과 내부 판단 규칙을 연결할 필요가 있었다.

#### 핵심 판단: 요청 해석과 적합성 판단 분리

- LLM의 역할을 원하는 상품군과 금융사 등 요청 의도 해석으로 제한하고, 추천 가능 여부는 결정적인 코드 규칙으로 판단하도록 책임을 분리했다.
- 고객의 투자 성향과 자금은 대화에서 추출한 값이 아니라 MySQL의 최신 구조화 프로필을 사용했다. 입출금 자산을 가용자금 판단의 기준으로 삼고, 총자산이나 부동산을 즉시 투자 가능한 현금으로 간주하지 않았다.
- 조건을 충족하는 후보가 없을 때는 추천을 보류하도록 설계했다. 다른 금융사나 상품군으로 임의 대체하거나 추천 수를 채우기 위해 부적합 상품을 반환하지 않도록 변경했다.

#### 기술적 구현

1. **LangGraph 단계 분리**
   - `interpret → retrieve → validate → respond` 노드로 요청 해석, 후보 검색, 적합성 검증, 응답 생성을 분리했다.
   - 상품군별 최대 20개 후보를 조회한 뒤 검증을 통과한 상품만 최대 3개 반환했다. 일반 추천에서는 예금·적금부터 검색하고, 펀드를 반드시 포함하던 규칙을 제거했다.
   - 명시적인 상품군·금융사·제외 조건은 LLM 해석보다 우선 적용했다. “펀드는 원하지 않아”, “국민 말고 예금” 같은 부정 표현과 금융사 별칭도 검증 대상으로 포함했다.

2. **상품 적합성 정책 모듈**
   - 투자 성향과 상품 위험도를 교차 검증하고, 최소 가입금액과 가용자금, 요청 예산·기간, 금융사·상품군 일치 여부를 함께 검사했다.
   - 고위험 상품, 투자 성향보다 위험한 상품, 가입조건 미확인 상품, 판매 종료 상품, 확인 자료가 오래된 상품을 응답 생성 전에 제외했다.
   - 위험도나 고객 정보가 누락됐을 때 임의의 안전한 기본값으로 대체하지 않는 보수적 정책을 적용했다.

3. **위험등급이 없는 상품의 근거 기반 내부 분류**
   - 공식 위험등급을 뜻하는 `official_risk_grade`와 서비스가 계산하는 `risk_assessment`를 분리했다. 공식 등급이 없는 상품은 해당 값을 `null`로 유지했다.
   - 일반 원화 예금 구조와 예금자보호 대상 여부가 함께 확인된 상품은 내부적으로 낮은 위험으로 분류하고, 레버리지·파생·주식형·벤처 등 확인된 손실 노출 구조는 높은 위험으로 분류했다. 근거가 부족한 상품은 미확인으로 유지했다.
   - 사용자 응답에도 “공식 6등급”처럼 표시하지 않고 “내부 위험분류: 낮음”으로 안내했다. 예금자보호를 무조건적인 원금보장으로 해석하지 않았다.

4. **상품별 가입조건과 출처 관리**
   - 우리은행 WON플러스 예금, KB Star 정기예금, 카카오뱅크 정기예금의 공식 상품 안내·설명서에서 가입대상, 최소 가입금액, 가입기간, 보호 여부를 정리했다.
   - 각 사실을 `value`, `source_id`, `locator`로 저장하고 발행기관, URL, 문서기준일, 실제 확인일을 구분했다.
   - 상품군·금융사·상품명이 정확히 일치할 때만 근거를 연결했다. 동일 이름의 특판이나 다른 클래스에 유사매칭으로 근거가 전파되지 않도록 했다.
   - 30일을 초과한 근거, 미래 확인일, 원천 가입제한과의 충돌, 공시 종료를 차단했다. 재조회나 배치 실행만으로 근거 확인일을 갱신하지 않았다.
   - 검색 시 근거를 적용하는 경로와 기존 JSON·MongoDB 상품을 일괄 보강하는 도구를 구현했다. MongoDB는 기본 dry-run으로 상태별 건수를 확인하고, 적용 시 원천 데이터의 동시 변경을 검사해 변경된 행은 덮어쓰지 않도록 했다.

5. **비선호 이력과 응답 우회 방지**
   - 상품 ID 기준 싫어요 이력을 검증 단계에 전달해 다음 추천 후보에서 제외했다. 좋아요는 적합성을 통과한 동일 위험도 후보의 우선순위를 정할 때만 사용했다.
   - 챗봇이 검증된 상품 목록을 받은 뒤 별도 LLM 응답에서 다른 상품을 생성하는 경로를 제거했다. 상품명·금융사·가입금액·추천 이유는 검증 결과를 바탕으로 정형 응답으로 구성했다.
   - 일반 금융 개념은 검토된 설명문으로 제공하고, 검증되지 않은 개인별 상품·자산배분을 자유 생성하지 않도록 했다.

6. **판단 이력과 장애 처리**
   - MongoDB `recommendation_audits`에 요청 ID, 정책 버전, 판단에 사용한 고객 성향·자금, 요청 조건, 후보별 통과·제외 사유, 상품 근거 식별자, 원천 스냅샷 해시, 최종 추천 근거를 기록했다.
   - 고객 원천 정보, 피드백 조회, 상품 검색 또는 감사 기록 저장이 실패하면 추천을 보류했다. 추적할 수 없는 추천이 사용자에게 전달되지 않도록 저장 이후 응답을 반환했다.
   - 기존 API 응답 구조를 유지하면서 `request_id`, `status`, `message`를 추가해 정상 추천·적합 상품 없음·검증 불가 상태를 구분했다.

#### 성과와 검증

- **동일한 300개 평가 데이터셋에서 부적합 상품 추천률을 18%에서 2%로 낮췄다.** 감소 폭은 **16%p**이며, 검색 Recall@K나 일반 질의 응답 성공률과 구분되는 추천 적합성 지표다.
- 추천 기준을 프롬프트의 준수 여부에 맡기지 않고 코드 정책으로 적용해, 위험 성향·가입조건·비선호 이력에 따른 제외 기준을 일관되게 처리했다.
- 추천 근거와 제외 사유를 남겨 잘못된 추천이 발생했을 때 요청 해석, 검색 후보, 적합성 판단 중 어느 단계가 원인인지 추적할 수 있도록 했다.
- 추천·상품 근거·최신 고객 정보·기존 관련 기능의 선별 회귀 테스트 **99개 통과**. 외부 LLM·DB IO 대역을 활용해 미확인 데이터, 부정 표현, 금융사 불일치, 비선호 이력, 장애 시 추천 보류, 동시 갱신 방어를 검증했다.
- 동일 case_id의 정답과 변경 전후 실제 상품 ID를 비교하는 평가 도구를 구현했다. 부적합 상품 비율과 함께 부적합 응답 비율·추천 제공률을 계산하고, 중복·누락 사례와 중복 상품 ID를 거부하도록 했다.

### 1-D. 노후하우 LLM API 호출 관리: 사용자 인증·분산 한도·재시도·토큰 계측

- 구분: 노후하우 동일 코드베이스의 후속 고도화, 2026.11.02
- 역할: 기존 사용자별 LLM 호출량 모니터링을 공통 호출 게이트웨이와 실제 호출 제어로 확장
- 주요 기술: Python, FastAPI, Redis Lua·Sorted Set, httpx, MongoDB, PyJWT, asyncio, Next.js, TanStack Query, Docker, Pytest
- 핵심 검증: **실제 Redis에 5개 연결로 500개 요청을 경쟁시켰을 때, 전체 한도 54회 설정에서 정확히 54개만 허용**. 실제 Redis·MongoDB 통합 검증과 기존 상품 적합성 회귀를 포함한 **89개 테스트 통과**, 프런트엔드 타입·변경 파일 린트 검사 통과.

#### 문제 상황과 판단

- 공용 API Key를 사용하는 AI 기능에서는 사용자별 호출 집중과 전체 한도 소진을 함께 관리해야 했다. 기존 모니터링 API와 대시보드는 사용 현황을 보여주지만 호출 자체를 제한하지는 못했다.
- 기존 AI 서버는 요청 본문의 `user_id`를 사용했고, 대화 건수만으로는 실제 외부 호출·재시도·토큰 사용량을 정확히 구분할 수 없었다.
- 사용자별 한도를 균등 고정 배분하면 공용 한도가 남아 있어도 활용하지 못한다. 전체 한도와 개인별 과도한 사용 제한을 함께 적용하고, 여러 서버가 같은 제한 상태를 공유하는 구조를 선택했다.
- SDK 내부 재시도가 호출 제한과 집계를 우회하지 않도록 실제 외부 HTTP 호출 한 번을 제어·계측의 기본 단위로 정했다.

#### 기술적 구현

1. **인증된 사용자 기준의 공통 호출 경로**
   - 기존 Spring 접근 토큰과 동일한 HS512 서명을 검증하고, 만료시간·JWT subject·권한 정보를 확인했다. 로그아웃 토큰은 기존 Spring 블랙리스트 Redis에서 검사했다.
   - 요청 본문·경로의 사용자 ID가 토큰 사용자와 다르면 403으로 차단했다. 관리자 API와 수동 벡터화에는 `ROLE_ADMIN`을 적용했다.
   - `get_llm().ainvoke()`를 공통 게이트웨이 어댑터로 전환하고, `ContextVar`로 인증 사용자·기능·요청 ID를 전달했다. API Key는 서버에서 관리하며 요청·사용량 기록에 노출하지 않았다.

2. **Redis 기반 전체·사용자별 호출 제한**
   - Sorted Set으로 최근 60초의 호출 기록을 관리하고 Lua 스크립트에서 전체·사용자별 한도와 모델별 동시 실행 슬롯을 원자적으로 검사·확보했다.
   - Redis `TIME`으로 서버 간 시계 차이를 피하고, 관련 키를 동일한 Cluster 해시 슬롯에 배치했다. 거절된 요청은 전체·사용자 한도를 소비하지 않도록 검사와 차감을 분리했다.
   - 기본 정책은 전체 분당 54회·사용자별 분당 30회·모델별 동시 실행 4개로 구성하고 환경변수로 조정하도록 했다. 공급자 분당 한도 60회를 가정한 설정 예시이며, 사용자 5명에게 각각 12회를 고정 배분하지 않고 남은 공용 한도를 활용하는 방식이다.
   - Redis 장애 시 프로세스별 제한으로 우회하지 않고 503으로 외부 호출을 차단했다.

3. **동시 실행·취소·시간 제한**
   - 모델별 실행 슬롯에 75초 임대시간을 적용하고 정상 완료·오류·취소 시 반환했다. 프로세스 종료로 반환하지 못한 슬롯은 만료 후 회수하도록 했다.
   - 호출 허용 검사·사용량 저장·공급자 대기를 포함하는 작업 제한시간을 60초로 설정했다. 마지막 정리에는 슬롯 반환 2초·기록 저장 3초의 별도 제한을 두고 정리 도중의 취소도 처리했다.
   - SSE 첫 청크를 미리 준비해 호출 제한을 HTTP 200 내부 메시지가 아닌 실제 429와 `Retry-After`로 전달했다. 준비 중 브라우저 연결이 끊기면 대기 작업을 취소하도록 했다.

4. **실제 호출을 기준으로 한 제한적 재시도**
   - Gemini·Groq를 비동기 `httpx`로 호출하고 연결을 재사용했다. SDK의 숨겨진 자동 재시도를 제거해 외부 호출마다 한도 검사와 기록을 거치게 했다.
   - 공급자가 명시적으로 반환한 429만 최대 2회 시도하고, 초·HTTP 날짜 형식의 `Retry-After`, 지수 백오프와 지터를 적용했다. Redis에 공용 대기 시간을 저장해 다른 서버도 공급자 제한을 함께 준수하도록 했다.
   - 재시도도 새 호출로 한도에 포함했다. 대기 시간이 남은 작업 시간을 초과하면 조기 재시도하지 않고 429를 반환했다. 처리·과금 여부가 불분명한 시간 초과·네트워크 오류·5xx는 자동 재시도하지 않았다.

5. **사용량 기록과 토큰·비용 계측**
   - MongoDB `llm_usage`에 사용자·기능·공급자·모델·요청 ID·호출 시도 ID·상태·지연시간을 기록했다. 호출 전에 `started`, 이후 완료 상태를 저장해 정상 호출은 두 번의 저장으로 처리했다.
   - `attempt_id` 고유 인덱스와 upsert로 동일 호출의 중복 집계를 방지했다. 상태 버전을 비교해 늦게 완료된 시작 기록이 최종 결과를 덮어쓰지 못하게 했다.
   - 공급자가 반환한 입력·출력·전체·캐시 입력 토큰을 계측하고, Gemini의 추론 토큰도 출력 사용량에 반영했다. 답변이 차단되더라도 반환된 토큰 정보는 보존했다.
   - 사용량을 받지 못하면 0으로 추정하지 않고 미확인으로 남겼다. 비용은 운영자가 설정한 입력·출력 단가와 단가 스냅샷을 이용해 추정하고, 단가가 없으면 비용을 생성하지 않았다.
   - 성공 또는 429 결과의 마지막 기록 저장이 실패하면 계측 오류를 반환하고 추가 공급자 재시도를 막았다. 프롬프트·금융 프로필·모델 답변·인증키는 사용량 기록에서 제외했다.

6. **관리자 집계 API와 화면**
   - `/api/v1/admin/stats/llm-usage`에 사용자·기능·모델별 호출, 성공, 내부 차단, 공급자 429, 실패, 미완료, 토큰 미확인, 토큰 합계·추정 비용을 집계했다.
   - 서버 측 집계에 최대 90일 조회 범위, 5초 실행 제한, 최대 500개 그룹과 잘림 표시를 적용했다. 사용량 기록은 기본 90일 TTL로 보관하도록 했다.
   - Next.js `/admin/ai-usage`에서 기간·사용자 필터와 수동 새로고침을 제공했다. 자동 폴링과 LLM 호출 없이 관리 데이터를 조회하고, 기존 SSE 클라이언트에는 429·401 오류 안내를 추가했다.

#### 검증 결과와 의미

- **실제 Redis의 5개 연결에서 500개 경쟁 요청 중 설정 한도인 54개만 허용**되는 것을 확인했다. 이는 동시 접근에서도 공용 한도를 지키는 검증 결과이며, 초당 처리량이나 응답시간 개선율을 뜻하지 않는다.
- 실제 MongoDB로 호출 시도 중복 방지, 늦은 시작 기록의 덮어쓰기 차단, 사용자 필터, 토큰·비용 집계와 TTL 인덱스를 검증했다.
- 실제 Redis 블랙리스트와 JWT 인증, 사용자 ID 위조 차단, 서버 시작·종료, 슬롯 만료·회수, 연결 종료 시 취소, 재시도 한도, SSE 시작 전 429 전달, 기록 장애 시 재시도 중단을 검증했다.
- 호출 관리와 기존 상품 적합성 회귀 테스트 **89개가 통과**했다. 별도 시점의 적합성 관련 선별 테스트 99개와는 실행 대상이 다른 결과다.
- 모니터링에 머물던 기능을 인증·호출 허용·외부 호출·계측·관리자 조회까지 연결했다. 호출 감소율이나 비용 절감률을 새로 실측한 성과로 추가하지 않는다.

## 2. 신용카드 추천 AI 챗봇

- 구분: 우리FIS아카데미 프로젝트, RAG 기반 개인화 카드 추천 챗봇
- 역할: AI 추천 및 Spring 백엔드 개발과 부하 검증 참여. 개별 기능의 팀원별 구현 경계는 제출 전 최종 확인
- 기술: Spring Boot, Spring MVC, Spring WebFlux, FastAPI, LangChain RAGChain, SSE, k6, Grafana
- 문제 상황:
  - 이용자의 소비 성향과 사용 목적을 카드 혜택에 매핑해 추천 근거를 설명하는 기능 필요
  - LLM 응답 대기 시간이 긴 상황에서 Spring MVC 요청 스레드가 점유되어 높은 동시 부하에서 스레드 가용성 저하 가능
  - 클라이언트가 AI 서버를 직접 호출하는 구조라 서비스 서버와 AI 서버의 요청 경로, 인증 및 응답 형식을 각각 관리해야 하는 복잡성
- 판단과 구현:
  1. Spring과 FastAPI를 연결하고 LangChain RAGChain으로 카드상품 검색 결과를 기반으로 혜택과 추천 근거를 JSON 형식으로 반환하도록 구성했다.
  2. 동일 추천 기능을 Spring MVC와 Spring WebFlux 서버에서 비교하고, 외부 LLM 대기 같은 I/O 중심 요청에 Non-blocking 처리 방식을 적용했다. WebFlux가 모든 조건에서 빠르다고 일반화하지 않는다.
  3. SSE를 적용해 **LLM 생성이 끝나기 전부터 답변을 순차 전달**하고 리액티브 스트림으로 AI 서버 응답을 Spring 서버에서 중계했다.
  4. **Proxy 방식의 단일 Gateway 진입점**을 구성했다. 기존 클라이언트 → AI 서버 직접 호출을 클라이언트 → Spring 서버 → AI 서버 구조로 전환해 클라이언트의 서버별 호출 의존성을 줄이고 라우팅을 백엔드에서 관리했다. _GoF Proxy 패턴 자체를 구현했는지, 별도 Spring Cloud Gateway 제품을 썼는지는 구분해 확인한다._
  5. k6와 Grafana로 **500 VU 부하 시나리오**의 MVC/WebFlux 스레드 사용량과 DB 조회 부하를 비교했다. VU 수는 실제 동시에 실행된 요청 수와 같다고 단정하지 않는다.
- 성과 및 구분:
  - **SSE 적용 후 응답 지연 약 35% 개선**: 최신 사용자 제공 성과. 최초 토큰 도착 지연(TTFT)인지, 첫 화면 표시 지연인지, 전체 응답시간인지 측정 구간 확인 필요. SSE만으로 모델의 전체 생성 시간이 35% 단축된 것으로 표현하지 않는다.
  - 과부하 테스트에서 **단일 서버 스레드 가용률 약 80% 향상**: 사용자 제공 결과. 개선 전후 스레드 수, 가용률 분모 및 평균/피크 기준 확인 필요. 80%p 증가와 동의어가 아니다.
  - Gateway 단일화로 **클라이언트의 AI 서버 직접 호출 의존성과 서버별 API 라우팅 관리 지점을 줄였다**. 별도 측정치가 없으므로 호출 횟수 또는 응답속도 단축률을 임의로 붙이지 않는다.
- 적합 문항: AI 서비스 백엔드, I/O 병목 분석, 비동기 설계, 실시간 응답, 서비스 간 연계, 부하 비교
- 확인할 사항: 500 VU 시나리오의 도착률과 지연 설정, 서버 사양, 비교 요청, TTFT/전체 응답시간 측정 방법, 스레드 가용률 정의, 정확한 개인 구현 범위

  - 인플루언서 특성과 광고 요구사항을 조합한 QA 데이터 1,000건 이상을 구축해 도메인 특화 질문의 할루시네이션 완화
  - 해시태그, 좋아요/댓글 수, 광고 글 비율, 팔로워 추이 등을 Chart.js 대시보드로 구현
  - Lazy Loading과 메모이제이션으로 렌더링 최적화
- 성과:
  - Recall@5: 0.59 → 0.88 (**+0.29 절대값, +29%p**; 동일 검색 평가 조건 가정). 이 수치는 노후하우 Recall@10과 별도
  - ROUGE-1 F1: 0.46 → 0.72 (**+0.26점**; 정답 답변과의 단어 중복도 개선)
  - nDCG@5: 0.61 → 0.74 (**+0.13점**; 추천 순위 품질 개선)
  - Lighthouse 기준 초기 렌더링 속도 40% 개선
- 적합 문항:
  - 문제해결, 도전, 리더십, AI 추천 시스템, 외부 API 리스크, 장기 프로젝트 완수
- 주의:

  - Notion API로 문제의 주차, 이름, 날짜, 원문 URL과 멤버별 풀이 페이지의 Java 코드, 전략, 후기를 구조화. SSAFY 스터디 활동에서는 Notion/GitHub MCP도 활용했다고 최근 확인됨. **MCP를 사용한 학습 및 작업과 서비스가 직접 호출하는 REST API 구현을 같은 호출 경로로 설명하지 않도록 구분 필요**
  - 중첩된 Notion 블록은 최대 깊이를 제한한 재귀 탐색으로 조회하고, `next_cursor`가 끝날 때까지 페이지네이션 처리
  - Notion에 코드가 없으면 GitHub 재귀 트리 조회로 후보 파일을 찾고, 문제명과 URL의 숫자 식별자를 정규화해 관련 Java 파일을 선택한 뒤 Raw Content API로 조회
  - 데이터 출처와 관계없이 코드, 전략, 후기, 언어, 출처 URL을 공통 `StudySolution` 타입으로 제공
  - 멤버별 코드 존재 여부를 기준으로 완료 문제 수와 주차별 진행률을 자동 계산해 메인 화면에 표시
  - 동일 데이터를 60초 안에 다시 요청하면 서버 메모리 캐시를 반환하고, 처리 중인 동일 요청은 기존 Promise를 공유하도록 구현
  - 사용자가 즉시 동기화를 요청할 때는 캐시를 우회하도록 `refresh` 옵션 구현
  - AI 리뷰 자동 실행을 제거하고 사용자가 버튼을 눌렀을 때만 호출하도록 변경
  - 문제 ID, 멤버 ID, 코드 내용을 조합한 키로 메모리와 LocalStorage에 리뷰를 캐시하고, 진행 중인 동일 요청은 Promise를 공유해 중복 호출 방지
  - 서버에서 문제와 코드 정보를 SHA-256으로 해싱하고, 리뷰 정책 변경 시 캐시를 갱신할 수 있도록 버전 값 포함
  - 초보자 관점에서 `코드 근거 → 발생 가능한 문제 → 수정 방법` 순서로 설명하고, 핵심 이슈는 2~3개, Java 예시는 최대 1개·12줄 이하로 제한하도록 프롬프트 개선
  - AI 응답을 JSON으로 받고 필수 필드, 이슈 유형, 줄 번호, 이슈 개수, 코드 예시 길이를 런타임에서 검증·정규화
  - Java 예약어, 문자열, 숫자, 애노테이션, 연산자, 주석 등을 분석하는 경량 구문 강조기를 구현하고 AI의 지적 줄을 코드 뷰어에 표시
  - `dangerouslySetInnerHTML` 없이 제한된 Markdown 문법을 React Node로 변환하고 HTTP·HTTPS 링크만 허용
  - 약 300줄 규모의 상세 페이지를 코드 뷰어, Markdown 렌더러, AI 리뷰 Hook, 공유 타입, Route Handler로 분리
- 성과:
  - 분산된 문제, 제출 현황, Java 풀이 코드, 전략과 후기를 하나의 서비스에서 확인할 수 있도록 통합
  - 스터디원 4명의 주차별 제출 현황과 진행률을 자동으로 파악할 수 있게 함
  - 필요할 때만 AI 리뷰를 요청하고 동일 코드의 결과를 재사용해 불필요한 API 호출을 줄임
  - 특정 구성원의 시간에 의존하던 리뷰를 스터디원이 필요할 때 받을 수 있는 구조로 전환
  - AI 출력 편차가 있어도 프론트엔드가 안정적으로 표시할 수 있는 응답 검증 체계 구축
  - 데이터 통합, 운영 자동화, AI 사용량 관리, 유지보수성 개선을 하나의 서비스 흐름으로 연결
- 적합 문항:
  - 사용자 불편 개선, 업무 자동화, AI 활용, 비용·사용량 관리, 외부 API 연동, 데이터 통합
  - 운영 효율화, 코드 품질, 유지보수성, 자기주도 개발, 스터디 협업
- 주의:

  - ‘비용 절감’보다는 중복 호출 방지와 사용량 통제 구조를 구현했다고 표현

  - 이후에는 구현 전에 실제 사용자의 필요와 서비스 참여 가능성을 먼저 확인하려는 기준이 생겼고, 이 문제의식이 EasyReader의 실제 배포와 사용자 피드백 확인으로 이어짐
- 적합 문항:

### 16.2 KnowWhoHow 관리자 통계·채팅 로그 API — 데이터 접근 구조 개선

**문제 상황**

- MySQL 사용자 목록을 가져온 뒤 반복문 내부에서 사용자별 MongoDB 채팅·피드백 통계를 추가 조회하는 구조였다.
- 최근 채팅 API에서도 MongoDB 집계 결과의 사용자마다 MySQL에서 이름을 조회하면서 connection 획득·반환이 반복됐다.
- 따라서 사용자 수 `N`이 증가할수록 DB Query와 네트워크 round trip이 함께 증가하는 **N+1 유사 패턴**이었다.
- `재현 테스트 필요`: 사용자 수 10 / 50 / 100 / 500명으로 늘리며 기존·개선 API의 평균, p95, Query 수, DB connection 사용량을 비교한다.

**원인 판단**

- 개별 SQL이나 MongoDB 쿼리 한 건의 속도보다 **애플리케이션 반복문 안에서 DB I/O를 수행하는 접근 구조**가 확장성을 떨어뜨리는 원인이라고 판단했다.
- MySQL과 MongoDB를 동시에 사용하는 구조라 DB 간 Join이 불가능하므로, 각 저장소가 잘하는 집계를 맡기고 애플리케이션에서는 결과만 조합하는 구조가 필요했다.

**해결**

- 페이지의 `user_id`를 먼저 수집했다.
- MongoDB에서는 `$match + $in + $group` Aggregation으로 채팅·피드백 통계를 사용자별로 일괄 집계했다.
- MySQL에서는 `WHERE IN` Batch Query로 사용자 이름을 일괄 조회했다.
- 두 결과를 `user_id → 통계/이름` Dictionary·Map으로 변환해 반복문에서는 추가 DB I/O 없이 메모리에서 조합했다.

**성과**

- `검증 완료`: 사용자 수에 비례해 증가하던 반복 DB 조회를 **고정된 수의 Batch Query와 Aggregation 중심 구조**로 전환했다.
- `검증 완료`: 반복문을 DB I/O 구간이 아닌 Dictionary/Map 기반 결과 조합 구간으로 변경했다.
- `재현 테스트 필요`: 개선 전후 p95, 평균 응답시간, Query/round trip 수를 실제 로그와 부하 테스트로 확정한다.

**권장 측정 도구**

- FastAPI 계열 API: `k6` 또는 `Locust` + Prometheus/Grafana
- MySQL: SQLAlchemy query logging/event, connection pool 지표
- MongoDB: PyMongo Command Monitoring 또는 profiler
- 핵심 지표: p95, req/s, Query 수, Mongo command 수, DB connection 사용량

### 16.4 KnowWhoHow 금융상품 RAG — 테스트셋 기반 AI 검색 품질 개선

**문제 상황**

- Vector Search만 사용했을 때 의미적으로 비슷한 상품은 찾았지만, 상품 유형·사용자 조건처럼 반드시 만족해야 하는 정형 조건을 충분히 보장하지 못했다.
- `검증 완료`: Baseline 검색 성능은 **Recall@10 0.68, NDCG@10 0.64**였다.
- 평가셋의 정확한 질의 수와 정답셋 구성 방법은 추가 확인 필요.

**실패 분석**

- 단순히 LLM 모델의 생성 능력을 문제로 보지 않고 **검색 단계에서 정답 후보가 빠지는지**를 먼저 확인했다.
- 실패 케이스를 `정형 조건 누락 / 의미 유사도 편향 / 후보 순위 문제 / 데이터 최신성` 등으로 분류해 검색 구조를 개선하는 방식으로 접근한다.

**해결**

- Vector Search 단독 구조에서 Keyword/의미 검색을 결합한 Hybrid Search로 변경했다.
- Metadata Filtering을 적용해 반드시 만족해야 하는 조건을 먼저 제한했다.
- 후보 결과에 Reranking을 적용해 상위 결과의 순위를 다시 조정했다.
- 후보 검색 범위와 Reranking 대상을 조정해 품질과 Latency를 함께 최적화했다.

**성과**

- `검증 완료`: **Recall@10 0.68 → 0.85**.
- `검증 완료`: **NDCG@10 0.64 → 0.79**.
- `기록 충돌 확인`: Recall@10 0.85를 유지한 응답시간 최적화로 표기할 수 있으나, 평균 검색시간 **약 42% 또는 약 50% 단축** 기록이 혼재한다. 테스트 조건 확인 전 자기소개서에 비율 사용을 보류한다.

**AI 평가 작성 원칙**

- 개선 전후는 반드시 **동일한 테스트셋**으로 평가한다.
- 테스트셋에는 일반 질의뿐 아니라 정형 조건, 복합 조건, 모호한 표현을 포함한다.
- 검색 품질은 Recall@K, NDCG@K, MRR 등을 사용하고, 생성 품질은 정답률·근거 없는 답변 비율·ROUGE 등 목적에 맞는 지표를 별도로 본다.
- 검색 품질과 서비스 속도를 섞지 않고 `품질 지표`와 `시스템 지표`를 분리해 기록한다.

### 16.5 COLLABO / 인플루언서 추천 — 외부 API 변경과 Hybrid RAG 전환

**문제 상황**

- Meta Graph API 정책 변경으로 팔로워 성별·연령 등 기존 추천 Feature를 안정적으로 수집하기 어려워졌다.
- 기존 규칙 기반 및 스태킹 방식은 외부 데이터 의존성이 높아 동일한 추천 구조를 계속 유지하기 어려웠다.

**원인 판단**

- 모델 자체보다 **필요한 Feature를 지속적으로 확보할 수 없는 데이터 수집 구조**가 핵심 리스크라고 판단했다.
- 정형 조건과 자연어 요구사항을 하나의 방식으로 처리하려는 것도 한계였다.

**해결**

- 정형 조건은 SQL로 직접 조회하고 비정형 요구는 Vector Search로 처리하는 Hybrid RAG 구조로 변경했다.
- 인플루언서 특성과 광고 요구사항을 조합한 QA 데이터 **1,000건 이상**을 구축해 도메인 질문의 할루시네이션을 줄였다.
- 관련 논문을 조사하고 협력기업의 기술 검토를 반복해 구조 변경의 타당성을 확인했다.

**성과**

- `사용자 확인`: **Recall@5 0.59 → 0.88** (+0.29).
- `사용자 확인`: **ROUGE-1 F1 0.46 → 0.72** (+0.26).
- `사용자 확인`: **nDCG@5 0.61 → 0.74** (+0.13).
- `검증 완료`: Lighthouse 기준 **초기 렌더링 속도 40% 개선**.

**AI 평가 보강 시 주의**

- QA 데이터 1,000건 이상을 구축했다. 지식 데이터와 정답 답변을 마련했으며, 전체 데이터가 모두 평가용 테스트셋이었다고 단정하지 않는다.
- ROUGE-1 F1과 nDCG@5는 2026-10-10 사용자 확인 값을 유지했고, Recall@5는 2026-10-18 사용자 정정 값 0.59→0.88로 갱신했다. 기존의 포괄적인 “추천 성능 30% 이상 향상” 대신 지표별 수치를 사용한다.
- ROUGE-1 F1은 정답 답변과의 단어 중복도 지표이며, 추천 정확도나 의미적 정답률로 표현하지 않는다.
- 자기소개서용 표현: 1,000건 이상의 QA 데이터셋을 구축하고, 벡터 검색과 키워드 검색을 결합한 Hybrid RAG를 적용했습니다. 기존 검색 방식과 비교 평가한 결과, Recall@5는 0.59에서 0.88로, ROUGE-1 F1은 0.46에서 0.72로 향상되어 관련 정보 검색률과 답변의 정답 유사도를 개선했습니다. 추천 순위 품질을 나타내는 nDCG@5도 0.61에서 0.74로 향상됐습니다.
- 실제 자기소개서에는 `평가셋 규모 / 정답 기준 / Baseline / 개선안 / 동일 평가셋 결과`가 확인되는 경우에만 상세 숫자를 추가한다.
- 보강 데이터와 평가 데이터를 같은 셋으로 사용했다면 과적합 가능성을 설명할 수 있어야 한다.

### 16.6 배달 공동구매 매칭 플랫폼 — 실시간 매칭 성능 최적화

**문제 상황**

- 기존 Gale-Shapley 기반 매칭 구조는 후보를 반복 탐색해 데이터가 증가할수록 실시간 요청 처리에 부담이 커졌다.
- `검증 완료`: JMeter **3,000건 매칭 요청** 기준 평균 응답시간 **1,745ms**.

**원인 판단**

- 매 요청마다 매칭 후보를 반복 탐색하고 이미 매칭된 사용자를 계속 확인하는 과정이 비용을 키운다고 봤다.

**해결**

- 브랜드별 대기열을 Queue로 분리했다.
- Bloom Filter를 이용해 특정 주문자의 매칭 여부를 빠르게 확인하도록 탐색 구조를 변경했다.

**성과**

- `검증 완료`: 동일한 3,000건 조건에서 평균 응답시간 **1,745ms → 81ms**.
- `검증 완료`: 약 **95% 응답시간 단축**.

**연결 포인트**

- 데이터 규모 증가 → 병목 발견 → 자료구조/알고리즘 변경 → 동일 조건 재측정의 흐름이 명확한 Backend 성능 개선 사례.

### 16.7 KnowWhoHow Airflow — 1,326개 금융상품 파이프라인 자동화

**문제 상황**

- 예·적금, 펀드, 연금저축 등 **총 1,326개 금융상품**을 수집·전처리·임베딩·적재해야 했다.

**원인 판단**

- 단순 Cron이나 수동 실행으로는 `수집 → 전처리 → 임베딩 → 적재 → 만료 삭제 → 누락 재처리`의 의존관계와 재실행 범위를 관리하기 어렵다고 판단했다.

**해결**

- Airflow DAG로 단계별 Task의 실행 순서를 명시했다.
- 매일 새벽 3시 Batch로 자동 실행했다.
- 만료 상품 삭제와 임베딩 누락 상품 Backfill을 후속 Task로 연결했다.

**성과**

- `검증 완료`: 1,326개 상품을 대상으로 반복 가능한 자동 파이프라인 구축.
- `검증 완료`: 실패·누락 상품을 재처리하는 Backfill 구조 마련.
- `재현 테스트 필요`: Task별 처리시간, 전체 DAG 실행시간, 실패/재시도 건수, 수동 개입시간을 로그로 측정하면 운영 효율 수치를 만들 수 있다.

### 16.9 EasyReader — AI 기능 평가 보강 계획

**현재 확인된 사실**

- Readability 우선, 실패 시 `body.innerText` fallback으로 본문을 추출한다.
- LLM을 활용해 쉬운 표현과 핵심 내용을 요약한다.
- TTS, 고대비, 글자 크기 조절을 제공하고 Chrome 웹스토어에 배포했다.

**추가로 만들 수 있는 AI/서비스 테스트셋 — 재현 테스트 필요**

- 뉴스, 블로그, 공공기관 공지, 쇼핑 상세, 문서형 페이지 등 웹페이지 50~100개를 유형별 테스트셋으로 구성한다.
- 본문 추출 성공률, Readability 실패율/fallback 비율, 요약 핵심정보 포함률, 근거 없는 요약 비율, 평균 요약 응답시간, TTFT를 측정한다.
- 추출 실패 페이지를 유형별로 분석한 뒤 DOM selector 보완, fallback 우선순위, 프롬프트 구조를 개선하고 동일 테스트셋으로 재평가한다.
- 사용자 평가가 가능하면 5점 척도로 `이해도 / 핵심정보 보존 / 읽기 편의성`을 측정한다.

### 16.10 알고리즘 스터디 AI 코드 리뷰 — AI 품질·호출 효율 평가 보강 계획

**현재 확인된 문제**

- 초기에는 페이지 진입 시 AI 리뷰가 자동 호출되어 불필요한 토큰·호출 한도를 사용했다.
- AI 설명이 추상적이라 초보자가 실제 코드 수정으로 연결하기 어려웠다.
- 동일 코드에 대한 중복 호출 가능성이 있었다.

**해결**

- 사용자 버튼 클릭 시에만 AI 리뷰를 요청하도록 변경했다.
- 코드·문제·사용자 기반 키로 결과를 캐시하고 진행 중인 동일 요청은 Promise를 공유했다.
- `코드 근거 → 발생 가능한 문제 → 수정 방법` 구조의 프롬프트와 JSON 응답 검증을 적용했다.

**추가 AI 평가셋 — 재현 테스트 필요**

- Java 알고리즘 풀이 30~50개를 난이도·오류 유형별로 선정한다.
- 사람이 만든 기준 답안과 비교해 `실제 오류 탐지율 / 잘못된 지적 비율 / 수정 가능성 / 근거 줄 번호 정확도`를 평가한다.
- Prompt Before/After를 동일 코드셋으로 평가한다.
- 시스템 측면에서는 동일 코드 반복 요청 시 API 실제 호출 횟수, cache hit rate, 평균 응답시간을 측정한다.

   - 순위 오류
   - 근거 없는 생성
   - 형식 오류

   - Baseline과 동일 조건으로 결과 비교

## 23. AI 기반 면접 학습 플랫폼 및 상태 그래프·실행 하네스 (2026.11.05 추가)

- 구분: 개인 면접 학습 플랫폼 개발 및 면접 에이전트 고도화
- 역할: 플랫폼 기능 기획, 회사별 학습 관리, AI 면접 흐름, 공통 실행 하네스 설계·구현 및 검증
- 정리 기준일: 2026-11-05. 이전 경험 카드와 구분되는 신규 프로젝트이며, 기존 금융 추천·상담 에이전트의 성과를 이 프로젝트에 합치지 않는다.
- 구현 근거: `C:/interview-ai`, `docs/interview-agent.md`, `lib/ai/agent-graph.ts`, `lib/ai/agent-contract.ts`, `lib/ai/harness/`, `app/api/ai/route.ts`, `tests/interview-agent-graph.test.ts`, `tests/interview-harness.test.ts`.
- 주요 기술: Vercel 서버 API, Supabase Auth·PostgreSQL·RLS, AI SDK, Zod·JSON Schema, SSE, Groq·NVIDIA·Ollama API, Vitest.
- 핵심 상황:
  - 분야별 면접 질문 학습과 이력서·프로젝트 경험 기반 맞춤 면접을 하나의 서비스에서 제공하고자 했다.
  - 질문 생성과 답변 평가를 개별 모델 호출로만 구현하면 제공자 지연, 응답 형식 오류, 재시도 및 진행 상태를 기능마다 다르게 처리하는 문제가 있었다.
  - 질문마다 꼬리질문을 무제한 반복하거나 검증되지 않은 모델 응답으로 다음 단계를 진행하지 않도록, 실행 범위와 분기 조건을 통제할 필요가 있었다.

### 23-A. 면접 학습 플랫폼 구현

- CS·프런트엔드·백엔드·AI·인성·지원 동기·기업 비즈니스·프로젝트 분야의 질문, 모범답안 및 꼬리질문 학습 기능 구현.
- 이력서·프로젝트 설명과 지원 기업·산업·직무·경력·면접 유형·난이도를 입력받아 맞춤 면접 질문을 생성하도록 구성.
- 질문과 답안을 학습하는 학습형 모드, 사용자 답변을 제출하고 평가받는 대화형 모드 제공.
- 회사 폴더를 추가하고 질문을 회사별로 생성·저장·이동·수정·삭제할 수 있도록 구현. 회사 삭제 시 질문과 연결된 학습 기록을 유지하는 미분류 처리 적용.
- 개인 답변 저장, 선택형 꼬리질문 작성, 북마크, 학습 상태 및 카테고리별 학습 현황 제공.
- 모범답안·꼬리질문 답안·AI 개선 답변에 마크다운 렌더링을 적용해 강조·목록·코드·표의 가독성 개선.
- Supabase 인증과 사용자 소유 데이터 접근 제어를 적용하고, 로그인 전 임시 학습 기록과 회원 저장 기록을 구분.
- 기본 학습 질문은 정적 콘텐츠로 관리하고, 사용자 작성 질문·회사 폴더·답변·북마크·학습 상태는 회원 데이터베이스에 저장하는 역할 분리.
- Vercel·Supabase 운영 구성을 유지하고 AI API 키는 서버 환경변수로 관리. 별도 모델 추론 서버를 직접 운영하는 구조는 아님.

### 23-B. 상태 그래프 기반 면접 에이전트

- 문서 분석 → 질문 생성 → 사용자 답변 → AI 평가 → 출력 검증 → 다음 행동 결정 → 사용자 확인의 흐름 구성.
- 정확성·논리성·구체성·질문 적합성·실무 적용성의 다섯 영역을 평가하도록 출력 계약 정의. 영역별 점수는 0~100점이며 중복·누락을 검증.
- 모델은 답변의 점수·근거·강점·개선점을 생성하고, 서버의 고정 규칙이 다음 행동을 결정하는 방식으로 책임 분리.
- 전체 답변이 44턴 이상이면 종합 평가를 우선 제안. 그 외에는 최저 평가 영역이 70점 미만이고 현재 질문의 꼬리질문이 2회 미만일 때 해당 영역 중심의 꼬리질문 제안.
- 꼬리질문 조건에 해당하지 않으면 다음 질문으로 이동하고, 마지막 질문이면 종합 평가 제안. 마지막 질문에서도 조건을 만족하면 꼬리질문을 먼저 제안.
- 사용자 확인 후 제안된 행동을 실행하며 수동 진행도 허용. 완전 자율 실행보다 진행 이유를 확인하고 통제할 수 있는 구조를 선택.
- 다음 행동을 정하기 위한 별도 모델 호출 없이 검증된 평가 결과로 분기해, 분기 자체에는 추가 생성 토큰을 사용하지 않도록 구성.
- 대화형 면접에 에이전트 진행 스위치와 결정 이유·평가·검증·분기·사용자 확인 기록 표시.

### 23-C. 공통 실행 하네스 구축

- 문서 분석 `analyze`, 질문 생성 `generate`, 답변 평가 `evaluate`, 꼬리질문 `followup`, 종합 평가 `summary`의 다섯 작업을 등록된 도구로 정의.
- 도구별 출력 스키마·출력 토큰 한도·제공자 시도 시간을 공통 목록에서 관리하고, 실제 면접 API가 같은 실행 계층을 거치도록 통합.
- 입력 계약 확인 → 허용된 모델 확인 → 모델 실행 → 결과 검증 → 완료 또는 실패로 이어지는 요청 단위 실행 경로 구성.
- 질문 개수와 식별자 중복, 평가 영역 중복, 필수 필드 및 값 범위를 검증. 형식이 맞지 않는 결과를 정상 완료로 전달하지 않도록 처리.
- 최근 대화 일부를 길이 제한과 함께 전달하고, 종합 평가에는 답변 발췌와 개별 평가를 제공해 문맥 크기 관리.
- 도구별 출력 토큰 한도를 적용하고, 전체 실행 예산을 최대105초로 제한. 일반 제공자 시도는30초, NVIDIA 질문 생성 시도는75초로 구분.
- 대체 후보는 최대3개로 제한하고 기존 제한된 재시도 정책을 재사용. 사용자 동의가 있을 때만 다른 제공자로 전환하며, 논리 요청당 사용량 제한 확인은1회 수행.
- 취소 신호를 하위 모델 호출로 전달하고, 취소 이후 늦게 도착한 결과도 완료로 처리하지 않도록 차단.
- Groq GPT-OSS 20B를 기본값으로 설정하고 NVIDIA·Ollama 등 구성된 제공자와 허용 모델을 선택하도록 구현.
- 모델이 생성한 문자열로 임의의 도구·URL·터미널 명령을 실행하지 않고, 사전에 정의한 면접 작업만 호출하도록 범위 제한.
- SSE로 하네스 버전·요청 ID·순번·작업·실행 단계·경과 시간·제공자·모델·오류 코드를 전달. 클라이언트에서도 이벤트 계약을 검증하고 최근60개 기록까지 표시.
- 실행 기록에는 문서·사용자 답변 원문·API 키를 포함하지 않도록 관측 정보와 입력 데이터를 분리.

### 23-D. 제공자 장애 분석 및 복구

- 로컬 실행에서 NVIDIA 응답 지연 후 대체 모델로 전환되는 경로를 재현하고, 문서 분석과 질문 생성의 시간 초과를 확인.
- SSE 연결의 HTTP 200 응답과 실제 작업 성공을 구분하고, 응답 내부의 완료·오류 이벤트와 제공자별 처리 기록으로 실패 지점 추적.
- Groq의 엄격한 구조화 출력 모드에서 JSON 형식 오류를 재현한 뒤, JSON 모드로 응답을 받고 서버에서 스키마·도메인 조건을 검증하는 방식으로 수정.
- 합성 입력의 단일 로컬 확인에서 수정 후 문서 분석 약2.2초, 질문5개 생성 약3.7초로 완료됨을 확인. 이는 특정 시점·모델·입력의 관측값이며 대표 응답시간이나 개선율로 사용하지 않음.
- 제공자 인증·요청 한도·모델 미지원·시간 초과·응답 검증 실패·취소를 구분하고, 재시도 및 대체 모델 전환 가능 여부에 따라 처리.
- 모델이 가볍다는 이유만으로 빠르다고 가정하지 않고 실제 계정의 호출 결과를 확인해 기본 제공자 선택에 반영.

### 23-E. 검증 결과 및 자기소개서 활용 기준

- 확인된 검증:
  - 합성 답변을 사용한 실제 Groq 호출에서 답변 평가 → 서버 그래프 분기 → 부족한 영역 중심의 꼬리질문 생성을 확인.
  - 각 요청에서 입력 확인·연결·모델 실행·출력 검증·완료의 순서 있는 하네스 이벤트 확인.
  - 잘못된 입력과 출력, 미동의 대체 모델 호출, 허용되지 않은 모델, 취소 전후 실행, 대체 모델 전환 성공을 자동 테스트로 검증.
  - 2026-11-05 기준 전체37개 테스트 파일·116개 테스트 통과 및 프로덕션 빌드 성공. **116개는 플랫폼 전체 테스트 수이며 하네스 단독 테스트 수가 아님.**
- 활용 역량:
  - AI API 호출을 사용자 서비스의 인증·학습 데이터·진행 상태와 연결한 서비스 구현.
  - 모델 생성 결과와 서버 실행 권한·분기 규칙을 분리한 상태 그래프 및 하네스 설계.
  - 출력 계약 검증, 호출 예산, 취소 전파, 제공자 장애 복구 및 실행 추적을 통한 신뢰성 확보.
- 서술 예시:
  - “AI 면접 플랫폼의 분석·생성·평가 작업을 공통 실행 하네스로 통합하고, 출력 검증·제한된 재시도·제공자 대체·실행 추적을 적용했습니다. 검증된 평가 결과를 상태 그래프로 연결해 꼬리질문·다음 질문·종합 평가를 제안하고, 사용자가 진행을 확인하도록 구현했습니다.”
- 성과 및 범위 주의:
  - 별도 FastAPI·Spring 서버, LangGraph 프레임워크, 지식 그래프를 사용한 프로젝트라고 표현하지 않음. 현재 상태 그래프와 하네스는 직접 구현한 실행 구조임.
  - 등록된 도구는 면접 관련 모델 호출 작업이며, 모델이 웹 검색·데이터베이스·터미널을 자율적으로 조작하는 범용 에이전트는 아님.
  - 체크포인트는 기존 브라우저 세션 기반이며 서버 영속 워크플로, 분산 락, 정확히 한번 실행, 브라우저 종료 후 백그라운드 실행은 보장하지 않음.
  - 스키마 검증은 답변 내용의 사실성이나 평가 공정성을 보장하지 않음. AI 점수는 학습 보조용 추정치이며 채용 판단이 아님.
  - 운영 완료율·첫 시도 성공률·p95 응답시간·성공 건당 토큰 및 비용·분기 적절성은 추가 측정 대상. 테스트 통과를 운영 성능 향상이나 토큰 절감률로 바꾸어 쓰지 않음.
  - 구현 및 검증과 Vercel 최신 버전 재배포 완료는 구분하며, 실사용자 규모·상용 운영 실적은 확인된 기록 없이 추가하지 않음.

### 23-F. 변경 이력 (2026.11.05)

- 기존 §1~§22 및 정량 성과·수상·교육 기록은 변경하지 않고 신규 면접 플랫폼 경험 카드를 추가.
- 플랫폼 기능, 상태 그래프 분기, 공통 실행 하네스, 제공자 장애 대응, 실제 호출·자동 테스트 결과 및 구현 한계를 구분해 반영.
